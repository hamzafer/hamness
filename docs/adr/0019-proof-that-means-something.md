# 0019: Proof that means something

**Status:** accepted, 2026-10-24. Refines ADRs 0005 and 0012.

ADR 0005 made `verified` mean "a hamness checker passed a piece of evidence". The v1 review showed that was too easy to satisfy: `prove(command: "echo ok")` passed, the re-run used the read-only bash allow list so nobody was asked, a URL fetch could carry data anywhere, CI from any repo counted, and one early pass verified a task whatever came after. This ADR sets what counts.

**A command must be able to prove something.** `parseClaim` refuses, before anything runs:
- commands joined by `||`, `;`, a new line or `&`, and `!`: they can turn a failure into exit 0. Only `&&` and `|` join commands, and a pipe runs under bash's `pipefail`;
- words known only at run time (`$VAR`, `$(...)`, backticks);
- no-ops that set the exit code (`true`, `:`, `exit`, `set`, `trap`, ...);
- flags that make a check print, skip or pass without checking, by a denylist per runner (`src/tasks/proof-shape.ts`): for any runner `--help`, `--version`, `--collect-only`, `--if-present`, `--exit-zero`, `--no-error-on-unmatched-pattern`, `--passWithNoTests` in any spelling; `tsc -v --init --noCheck --clean`; make's `-i -t -n -k -q` (clustered too); `-DskipTests`, `-Dmaven.test.skip`; gradle `-x`; `go test -exec -toolexec -n -list`; pytest `--fixtures --setup-plan --markers`; and test filters that obviously select nothing (`-run '^$'`, `-k ''`) or skip everything (`--skip ''`). `--flag=value` is read as `--flag`, and words after `--` count. A denylist, not an allowlist of flag shapes, because real checks take too many legitimate flags to list; a filter that matches nothing in a less obvious way is caught at run time by the no-tests-ran check below, or not at all;
- commands made only of read-only or printing parts (`echo`, `printf`, `cat`, `ls`, `grep`, `test`, `git status` ...). A `sh -c` string is looked into.

A run that exits 0 but shows that no tests ran (`Ran 0 tests`, `no tests to run`, `No tests found`, only `running 0 tests` lines) fails.

**Two questions for a re-run: may it run, and does it count?** The re-run is checked as `prove_command`, but whether it may run is exactly the decision a `bash` call with that command would get: bash's rules (user and trusted project allow rules included, every deny and ask too), then the judge in auto mode, then the user; `yolo` runs it (bash denies still apply). Being on the proof list never lets a command run: a repo can't make `bun test` run unasked by listing it, since what `bun test` runs is the repo's to define (revised in the v1 verification pass; an earlier draft let the list grant running). Whether it **counts** is the proof command list: every part on the list, or a read-only helper (`cd` into a folder inside the session folder, the built-in read-only commands). The list: built-in test runners, builds, linters and typecheckers (`bun test`, `npm test`, `npm run build`, `pnpm test`, `cargo test`, `go test`, `pytest`, `make test`, `tsc`, `biome check`, `eslint` and their kin, see `src/safety/proof.ts`), the user config's `proof.commands`, and the project's `.hamness/config.json` `proof.commands`, each counted only once trusted (`hamness trust`, ADR 0020). Anything else asks the user: "count `X` as proof?". This is the user's call in every mode: the judge never decides it and `yolo` does not skip it. When both questions need the user, they are one prompt. "Allow always" saves the run permission as a project bash rule (as for any bash call) and the proof pattern to the user's `proof.commands`, never the project's, so a repo can't grow the list.

**A pass after the agent changed what the command runs is weak.** If, during the task, the agent wrote or edited (with its `write` / `edit` tools) a file that defines what a proof command runs, its pass is recorded **weak**, with the reason: `package.json`, `bunfig.toml`, Makefiles, `conftest.py`, `pytest.ini`, `pyproject.toml`, `setup.cfg`, `tox.ini`, jest / vitest / playwright configs, `Cargo.toml`, `go.mod`, ESLint configs, `tsconfig*.json` and their kin (see `src/tasks/checkers/command.ts`), and any file the command names through a flag such as `--preload`, `-exec` or `--config`. Like agent-written file evidence, a weak pass never verifies a task alone.

**A URL is a request out.** `prove url` passes safety as `prove_url`: no rule allows it by default, so the judge or the user decides (URL rules match the URL; "allow always" offers its origin). Hosts that resolve to loopback, private, link-local, CGNAT or other internal addresses are refused unless the user config sets `proof.allowPrivateUrls` (a local dev server). Redirects are followed by hand, only on the same host, each hop checked again. Known gap: the name is resolved before fetch resolves it again, so DNS rebinding is not caught.

**CI must be about this work.** The repo must be the session folder's GitHub repo (`gh repo view`). A commit must be in HEAD's history; a PR's head branch must be the current branch and its head commit in HEAD's history. Passing CI fills the task's PR URL and commit (shown in the dashboard with the branch the task started on).

**Files.** File evidence must be inside the session folder, symlinks resolved. A file the agent wrote with its own `write` / `edit` tools in the task is **weak**: it can pass, but never verifies a task alone. (A file written through `bash` is not detected as weak; file evidence shows an artifact exists, not that it is right.)

**The gate reads the latest evidence.** A task is verified only when the latest decided piece (passed or failed; `error` checked nothing and is skipped) passed, the latest strong piece (not weak) passed, and that pass was submitted after the task's last `write` / `edit` by any of its agents (one still running counts as now). So: fail after pass is unverified, an edit after the proof needs a new proof. `task_done` says why a task closed unverified. An implicit task closes unverified only with failed evidence, edits or subagents; one whose only evidence is `error` is dropped with that evidence (ADR 0012 updated).

**The rail shows checks.** Each checker run emits `check.start` and `check.end` and gets its own rail row (the newest three). Background shells have no rows: Pi's `bash` tool has no background mode (it waits for every command), so there is nothing to show; they come when Pi or a hamness tool adds one.

Consequences: agents must prove with real checks, and a repo whose checks are not on the list asks once per pattern. A check also asks to run unless a bash rule, the judge or yolo lets it, so a user who wants `bun test` to run unasked in ask mode adds a bash allow rule. What a listed command runs is still up to the repo (an `npm test` script can be `exit 0`); an agent edit to it through `write` / `edit` makes the pass weak, but an edit made through `bash` (`sed -i`, `echo >`) after or before the proof is not detected, neither as weak nor as a later file change. The list says which commands count, not that the repo's tests are good.
