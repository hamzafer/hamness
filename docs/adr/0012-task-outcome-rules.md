# 0012: Task outcome rules, the implicit turn task, and the gate in the database

**Status:** accepted, 2026-10-24

ADR 0005 sets the gate; this records the rules around it that the spec leaves open.

**Opening.** The agent opens a task with `task_start(goal)`, the user with `/task <goal>`. When a user turn starts with no open task, hamness opens an **implicit task** named after the prompt. A `task_start` or `/task` during that turn **promotes** it (same id, now explicit with the new goal), so the turn's spend so far counts toward the task. Only one task is open per session: a second `task_start` is refused. An explicit task stays open across turns, and across a daemon restart, until it is closed (or dropped at turn end with nothing done, below).

**Closing.**
- `task_done(summary)`: `verified` if the proof gate passes (ADR 0019: the latest evidence passed, after the last file change, and not only weak file evidence), else `unverified`, with one exception (amended 2026-10-25): an explicit task the agent opened (`task_start`, never the user's `/task`) that only read is **dropped** like an implicit chat turn below, and the tool tells the agent so. "Only read" is an allowlist: no evidence rows of any status, no subagents, and every tool call is a read tool (`read`, `grep`, `ls`, `find`, `glob`), a task tool, or bash that `bashReadOnly` clears (every command on the read-only list, no writing flag, no file redirect, nothing decided at run time, and parseable). An MCP call, an unknown tool or bash it can't classify (`python -c`, a script) is work, so the task closes `unverified`. Migration 0010 stores who opened a task (`tasks.opened_by`). An agent that opened a task for a question ("what's this repo about"), read files and closed it would otherwise leave a red `unverified` task for work that needed no proof. Refusing `task_done` with a hint was the other option; it would leave the task open across turns with nothing to close it, so dropping is cleaner. A task with an edit and no proof stays `unverified`. The system prompt also tells the agent to call `task_start` only for work that changes things or must be proven, not for questions, explanations, reviews or reading code.
- `/override [reason]` (user only, never an agent tool): the open task, or the last task if it is `unverified`, becomes `overridden`. A verified, abandoned or overridden task cannot be overridden.
- `/abandon [reason]` (user only): the open task becomes `abandoned`.
- An implicit task still open at turn end: `verified` when the gate passes; `unverified` with evidence that failed (not `error`, which checked nothing), or with `edit` / `write` calls or subagents (work that went unproven); otherwise it is **dropped** (with any `error` evidence): the row is deleted and its messages, model calls and tool calls keep no `task_id`. A chat turn is no task, so it doesn't drag down the verified rate, but its spend still counts in cost per verified task. `bash` alone doesn't count as an edit, since most commands only read.
- An explicit task the agent opened (amended 2026-10-25) that is still open at turn end with no evidence rows and no work by the implicit rule above (no failed evidence, no file changes, no subagents) is **dropped** the same way. In an end-to-end run the agent called `task_start`, its only action (`rm -rf`) was denied, and it never called `task_done`, so the task stayed open across turns with nothing to close it. A task with any work or any evidence row stays open across turns, and a task the user opened (`/task`) always stays. The cost: an agent that opens a task, only reads, and asks the user a question loses the task at turn end and opens a new one next turn.

**Accounting.** Rows the session stores carry the current task's id: the open task, or the one closed earlier in the same turn, so the agent's wrap-up after `task_done` counts toward it. A task's cost and tokens are the sum of its `model_calls`; its time is `ended_at - started_at`.

**Evidence.** `prove` validates the claim strictly (any result-like or unknown field is refused), stores it as a pending claim, runs the checker and writes its result; `src/tasks/proof.ts` is the only code that writes `evidence.status`. A command re-run passes the session's safety check as `prove_command`: bash's deny and ask rules, and the proof command list instead of bash's allow rules (ADR 0019), so `prove` cannot run what `bash` may not, and runs unasked only what counts as proof. `error` (blocked, aborted, `gh` missing) is not a pass. Migration 0006 holds the gate in SQLite too: evidence starts pending, gets one complete result and is then final; a task becomes `verified` only with passed evidence; a closed outcome is final except `unverified` to `overridden`.

**Verified rate** (amended 2026-10-25) is `verified / (verified + unverified)`: the share of the tasks the proof gate decided that it verified. `overridden` is the user's call over the gate and `abandoned` is work stopped before the gate ran, so neither is in the denominator; both are shown on their own (the outcome counts in `hamness stats`, the Tasks tile and table). An earlier definition, verified over every closed task, let abandoned and overridden tasks pull the rate down (40% in an end-to-end run with 2 verified, 1 unverified, 1 overridden, 1 abandoned; 67% now). The dashboard tile and `hamness stats` say the definition.

**Migrations** may now have gaps in their numbers (tickets claim numbers up front and land in any order); every migration not yet recorded runs, in version order.

Consequences: an agent that never calls `prove` and never edits files leaves no tasks at all, which shows as spend with no verified tasks rather than as a high rate. An agent can still reach the database file through `bash`; the triggers stop a plain `UPDATE`, the safety rules deny edits under the data dir, and a `sqlite3` command is not on the allow list, so it asks.
