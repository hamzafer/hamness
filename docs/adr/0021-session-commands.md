# 0021: Session commands reuse Pi's session machinery, and an open task follows `/new`

**Status:** accepted, 2026-10-25

The TUI gets Pi's interactive commands (`/new`, `/clear`, `/compact`, `/resume`, `/session`, `/thinking`, `/copy`, `/export`, `/name`, `/fork`) plus hamness's `/mode` and a list of skills and MCP servers. The daemon serves them as `/v1/sessions/:id/<action>` routes.

**Pi does the work.** Compaction is `AgentSession.compact`, thinking levels are Pi's (`getAvailableThinkingLevels`, `setThinkingLevel`), export is `exportToHtml` / `exportToJsonl`, `/copy` is `getLastAssistantText`, the name goes into Pi's file with `setSessionName`, and a fork is Pi's own: `SessionManager.createBranchedSession` at the entry before the user message (a fresh file with `parentSession` when it is the first message). hamness does not use Pi's `AgentSessionRuntime`, since the runner builds the `AgentSession` itself; a replacement starts a new runner and disposes the old one, the way the runtime's `newSession` / `switchSession` / `fork` do.

**A replacement replaces one session.** (Amended by ADR 0023: a cwd can have several live sessions, one per window that launched fresh; this was "one live session per cwd".) `/new`, `/resume` and `/fork` start the replacement first, writing its rows, the moved task and a fork's copied transcript in one transaction (a failure leaves the old session and its task as they were, and disposes the new runner), then end the old one: `session.replaced` goes to its clients, its subagents stop, its approvals are denied, its row gets `ended_at` and its main agent `done`. A resumed session is `running` again with no `ended_at`. After the old session ends, the new or resumed one is made the cwd's most recently updated session, the one `hamness -c` picks. While a replacement or compaction runs, `/mode`, `/thinking` and `/name` answer 409, so a setting never lands on a session that is ending. `/new` fires SessionStart with source `clear` and `/compact` with `compact`, as Claude Code does. `/new` and `/fork` keep the model, thinking level and session mode; `/resume` restores the stored ones.

**An open explicit task follows `/new` and `/fork`.** ADR 0012 keeps an explicit task open until it is closed. `/clear` mid-task is a context reset, not the end of the work, so the task moves to the new session (`tasks.session_id`) and its spend there still counts toward it. `/resume` leaves the current session's task on it (back when that session is resumed). There is never an open implicit task between turns, so none moves. A session holding an open explicit task is never lost: `/v1/sessions?cwd=` lists it and `hamness -c` can pick it even when it has no message yet. Such a session never had a prompt, so Pi never wrote its file; resuming it starts a fresh Pi file under the same hamness ids (there was no context to lose). The task stays where it is rather than moving back, so nothing is rewritten when a session ends. A fresh launch (ADR 0023) does not move it either: it stays on its session, and the new chat shows a one-line hint to `/resume` it.

**A fork copies the transcript, not the spend.** The forked session gets copies of the main agent's messages and tool calls before the fork point, so it shows the history it continues. Model calls stay with the original session: the spend happened once. To find the fork point, user message rows store Pi's entry id (`messages.external_id`, migration 0007); older rows without one cannot be forked from.

**Mode per session.** `/mode ask|auto|yolo` sets a mode for that session only, kept in `sessions.safety_mode` and held by the safety service, which uses it over the config's mode. `yolo` emits `safety.mode` with a warning for clients to show as a banner; `session.mode` in snapshots says the same.

**Export** without a path writes under `<dataDir>/exports`; a relative path is in the session's cwd; an existing file is replaced only with `overwrite: true`. A symlink at the path is refused, dangling or not: Pi writes into hamness's own folder and the copy to the path opens it with `O_NOFOLLOW`, and `O_EXCL` unless overwriting. The export is unredacted, like Pi's own file, because the user asked for it.

**Compaction is spend.** The summary call is a stored model call (no message), counted toward the open task only: a `/compact` after `/abandon` or `/override` charges no task.

**MCP tool counts** (2026-10-25): `GET /v1/sessions/:id/compat` adds `tools` to each `start` server: how many tools it has registered in the session, counted as Pi registers them. Pi's MCP client keeps its connection state private, so connected vs failed is not reported: above 0 means connected, 0 means connecting, failed or toolless.
