# 0020: One repo trust, per item, keyed on the project

**Status:** accepted, 2026-10-24. Refines ADRs 0006, 0016 and 0017.

A cloned repo can bring files that loosen safety or run code: allow rules and proof commands in `.hamness/config.json`, Claude Code hooks in `.claude/settings*.json`, and MCP servers in `.mcp.json`. Before this ADR each had its own gate (none for allow rules, a plain "trusted" flag per repo for hooks, a fingerprint per server for MCP), and the agent itself could write the files that feed them.

- **One command.** `hamness trust [dir]` trusts everything the repo brings, as it is now; `--show` lists each item as `trusted`, `not trusted` or `new or changed` (since the last trust), and `--revoke` forgets the repo. `hamness hooks trust` and `hamness compat approve` (without server names) are aliases. The command is the user's act, so it does not ask again.
- **Trust is per item.** Each project allow rule (`tool` + `pattern`), proof command, hook definition (event, matcher, command, args, timeout, async, onFailure) and MCP server definition is stored as a fingerprint (a hash of its JSON with sorted keys). An added or edited item is untrusted until the user trusts again, while the trusted ones keep working. Sets, not one hash of the whole file, so a subagent's worktree that lacks an untracked file (such as `settings.local.json`) still runs what the repo trusted.
- **What waits.** Untrusted project allow rules are left out of the rule list (`SafetyConfig.untrusted` lists them); project ask and deny rules always apply, since they only tighten. Untrusted hooks don't run and the session gets a notice. Untrusted MCP servers don't start. Proof commands (ADR 0019) count only when trusted. "Allow always" saves the user's choice to the project config and trusts that rule as it is saved.
- **The agent can't edit its way in.** Writes to `.claude/settings*.json`, `.mcp.json` and `.hamness/**` anywhere under the session's dir ask by default, and a project rule can't loosen that. Anything written another way still lands as an untrusted item. On a case-insensitive filesystem (macOS by default; hamness checks the session folder once), every path rule, these asks and the secret denies included, matches in any case, so `.MCP.json` and `.ENV` are caught too, whether the file exists yet or not.
- **Keyed on the project.** `projectRoot(cwd)` is the repo root, or for a git worktree the main repo's root (read from the `.git` file and `commondir`, as `git rev-parse --git-common-dir` would say, without running git); `projectKey` is its real path. Trust, MCP approvals and `.hamness/config.json` all use it, so a subagent's worktree shares its repo's settings.
- **Stored in hamness's user config,** under `trust.projects["<key>"]` in `<data dir>/config.json` (mode 0600), never in the repo or in Claude Code's files. The earlier `hooks.trustedProjects` and `compat.mcpApprovals` keys are no longer read (pre-release), so those repos need one `hamness trust`.
- **Other fixes in the same pass.** Project instruction, rule and skill files (and skill folders) must resolve, symlinks followed, inside the repo; others are skipped and listed by `hamness compat`. Hooks are read from the repo root's `.claude/` as well as the cwd's, and managed `managed-settings.json` hooks always run.
